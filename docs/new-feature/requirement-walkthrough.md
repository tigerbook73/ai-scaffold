# 走读（Walkthrough）功能 — 需求

## 一、目标

Walkthrough 是一个代码讲解工具，帮助用户逐步理解代码变更或全量代码的内容与意图。

适用场景：

- 理解他人（或自己过去）提交的变更
- Task 完成后做整体回顾
- 学习某段历史提交的演进过程
- 了解某个模块或文件的全量代码结构

---

## 二、核心概念

**Walkthrough（走读）**：一次完整的走读事务，包含走读目标、分组和进度。每个 git 分支同时只有一个活跃 walkthrough。

**走读目标**：本次走读的代码范围，可以是未提交变更、某个 commit range、指定文件/目录的变更，或指定文件/目录的全量内容。

**分组**：将走读目标拆分为若干讲解单元，每组按顺序讲解。分组在创建时生成，后续讲解按此执行。

**状态**：走读进度持久化到本地状态文件，支持跨 session 恢复。状态文件不提交入 git。

---

## 三、功能需求

### 3.1 创建（create-walkthrough）

用户指定走读目标，创建新的 walkthrough 事务：

| 调用方式                            | 走读目标                          |
| ----------------------------------- | --------------------------------- |
| `create-walkthrough`（无参数）      | 交互确认（见下方说明）            |
| `create-walkthrough <commit range>` | 指定 commit 范围，如 `main..HEAD` |
| `create-walkthrough <文件或目录>`   | 交互确认（见下方说明）            |

**无参数时**：根据当前工作区状态提示用户确认走读目标：

- 工作区有未提交变更 → 建议以未提交变更为目标
- 工作区干净 → 建议以最近一次提交为目标

**指定文件或目录时**：提示用户确认走读范围：

- 工作区有未提交变更 → 建议：该路径在 working tree 中的变更，或该路径的全量内容
- 工作区干净 → 建议：该路径在最近一次提交中的变更，或该路径的全量内容

用户也可以用自然语言自由描述走读范围，AI 按理解执行。若范围明显过大（如整个项目的全量内容），AI 需提示用户缩小范围。

创建时，AI 分析走读目标、生成分组，并立即提示进入第一组讲解。

若当前分支已有活跃 walkthrough，提示用户先恢复或确认覆盖。

### 3.2 分组策略

| 情况                                                                                   | 分组依据                                      |
| -------------------------------------------------------------------------------------- | --------------------------------------------- |
| 当前分支 `docs/tasks/` 下存在设计文档（`design.md` 或 `design-*.md`） | 按设计步骤分组，AI 将变更映射到对应步骤       |
| 无设计文档                                                                             | AI 按模块、功能边界等自动分组，并说明分组逻辑 |

单组内容过大时（如潜在输出超过 300 行），可进一步拆分。两种情况下 walkthrough 流程完全一致。

### 3.3 讲解行为

每组讲解内容因走读目标而异：
- **变更类走读**：变更了哪些文件、为什么这样变更、目的是什么；语法格式变更、注释增加等不影响逻辑的改动可略过
- **全量代码走读**：该部分代码的结构、功能与设计意图

每组讲解完成后，等待用户自然语言指令（继续下一组、提问、查询进度等）。

### 3.4 中断与恢复

支持两种恢复方式：

1. **退出 session 后恢复**：执行 `start-walkthrough` / `resume-walkthrough`（两者等价），从状态文件读取进度，从中断处继续。恢复前校验分组是否仍然有效：
   - 分组来自设计文档时：检查文档是否有变更；有变更则提示分组可能过时，由用户决定是否重建
   - 分组由 AI 自动生成时：检查走读目标与当前代码是否一致；不一致则提示失效，询问是否重建
2. **session 内恢复**：直接用自然语言（如"继续 walkthrough"、"下一步"、"到哪一步了"），AI 从当前 session 上下文接续，无需读状态文件，无需校验

### 3.5 完成与关闭

所有分组讲解完毕后，AI 输出完成摘要，等待用户确认（如"OK"）。确认后删除当前分支的状态记录，事务关闭。

---

## 四、约束

- **一分支一事务**：每个 git 分支同时只有一个活跃 walkthrough
- **显式触发**：所有行为均由用户主动触发，无任何自动行为
- **本地状态**：状态文件保存在本地，不提交入 git；walkthrough 关闭时删除当前记录，其他分支的过期记录无需主动清理

---

## 五、与 Task 系统的集成

Walkthrough 独立于 Task 管理系统，可在任何分支使用。

若当前分支 `docs/tasks/` 下存在设计文档，分组质量更好（按设计步骤对齐）；无设计文档时功能完整，仅分组依据不同。依赖方向为单向弱依赖，Walkthrough 可完全独立运行。

---

## 六、设计原则

显式触发、按需恢复、状态失效自检——无任何自动行为。

---

## 七、词汇表

AI 在处理自然语言指令时，需识别以下中英文对照关系：

| 英文               | 中文                | 说明                           |
| ------------------ | ------------------- | ------------------------------ |
| Walkthrough        | 走读                | 功能名称，两者完全等价         |
| create-walkthrough | 创建走读            | 初始化新的走读事务             |
| start-walkthrough  | 开始走读 / 恢复走读 | 恢复已有走读（与 resume 等价） |
| resume-walkthrough | 继续走读            | start-walkthrough 的别名       |
| Group / Grouping   | 分组                | walkthrough 中的一个讲解单元   |
| State file         | 状态文件            | 记录走读进度的本地文件         |
