# Review 功能 — 需求

## 一、定位与依赖

Review 是独立功能，可在任何 Git 分支上使用，不依赖 Task 管理系统。

与 Task 的关系：
- 若当前分支的任务目录下存在 `DESIGN.md`，Review 优先按设计步骤分组，体验更好
- 无 `DESIGN.md` 时，AI 自动分组，功能完整

依赖方向：Review → Task（单向、弱依赖、可选）

---

## 二、技能实现方式

Review 交互子命令（下一组、解释更多、结束等）以**自然语言**交互，逻辑内嵌在 `start-review` 的 skill prompt 中，不作为独立 skill 文件。

`resume-review` 是 `start-review` 的纯别名，两者行为完全一致。

效果：
- 未调用 `start-review` 时，review 逻辑完全不在 session context 中，零干扰
- 调用后，完整交互规则进入 session，后续用自然语言推进即可

---

## 三、状态文件

- 本地文件，git 忽略，不提交入库
- 按分支名索引，一个分支同时只有一个活跃 review 事务
- 记录内容：当前分组进度（第几组）、review 的目标（commit range / work tree 快照标识）
- 无需主动清理；start-review 时若状态文件与当前代码不匹配，自动提示失效

---

## 四、分组策略

| 情况 | 分组依据 |
|------|---------|
| 有 DESIGN.md | 按设计步骤分组，AI 将变更映射到对应步骤 |
| 无 DESIGN.md | AI 自动分组（按模块、功能边界等），并说明分组逻辑 |

两种情况下 review 流程完全一致，只是分组来源不同。

---

## 五、Review 行为

- 按分组逐一讲解：每组变更了哪些文件、为什么这样变更、目的是什么
- 语法格式变更、注释增加等不需要详细说明，可略过
- 支持中途打断，下次 start-review 继续
- 支持查询当前进度（第几组 / 共几组）

---

## 六、场景

**场景 A：首次启动 review**
`start-review` → 无状态记录 → AI 分析变更、生成分组 → 从第一组开始讲解

**场景 B：中断后恢复 / 查看进度**
`start-review`（或 `resume-review`，两者等价）→ 读状态文件 → 展示当前进度（第几组 / 共几组）及选项：继续 or 重新开始

**场景 C：状态文件与当前代码不匹配**
`start-review` → 读状态文件 → 发现目标 commit 不存在 / work tree 已变更 → 提示"历史 review 已失效"，询问是否丢弃并重新开始

**场景 D：学习技术（无任务上下文）**
`start-review <commit range 或文件范围>` → AI 自动分组讲解 → 同样记录进度，按分支存状态

**场景 E：close-task 后**
状态文件留在本地，不清理。下次 start-review 时若代码已删除/合并，触发场景 C 自动提示失效。

---

## 七、设计原则

显式触发、按需恢复、状态失效自检——无任何自动行为。
