# Task 管理系统 — 需求

## 一、目标

Task 管理系统帮助用户规划、执行和交付中等规模的开发任务。

每个 Task 以一个 PR 为单位交付，贯穿需求识别、设计和实现三个阶段，全程维护过程文档，完成后随 PR 合并一并清理。

当前支持的 Task 类型：

- 特性（Feature）
- 重构（Refactor）

---

## 二、核心概念

**Task**：一个中等规模或复杂度的开发任务，通常需要数小时至数天完成，以一个 PR 为单位交付。每个 Task 独占一个 Git 分支。

**阶段**：每个 Task 经历三个阶段——需求识别（What）、设计（How）、实现。阶段之间可以有迭代，非严格线性；代价越往后越大，鼓励在前期把事情做清楚。

**步骤**：设计阶段划分的实现单元，每个步骤通常对应一个 commit，可单独测试和验证。多个步骤不得合并在同一 commit 中提交。

**任务文档**：记录 Task 全生命周期的过程文档，存放在 `docs/tasks/{task-name}/` 下，PR 合并前删除：
- `requirements.md`：需求（可拆分）
- `design.md`：设计（可拆分）
- `task-state.md`：任务状态与文档索引（主跟踪文档，不可拆分）

**task-state.md**：文档列表与任务进展的单一来源。提交记录是兜底依据，代表真实已提交的进展。

---

## 三、功能需求

### 3.1 创建任务（create-task）

在主干分支上创建新 Task：
- 创建 Git 分支，命名规范：`feature/{task-name}`（Feature）或 `refactor/{task-name}`（Refactor）
- 在 `docs/tasks/{task-name}/` 下初始化 `requirements.md`、`design.md`、`task-state.md`
- 自动进入任务工作模式（等同执行 start-task）

**输入**：任务名称（kebab-case）、任务类型

**前提条件**：
- 当前在主干分支（main / master）
- 工作区干净（无未提交变更、无新文件）
- `docs/tasks/` 下不存在已有任务目录

### 3.2 进入任务工作模式（start-task / resume-task）

建立当前 session 的任务上下文，使后续自然语言指令默认针对当前任务执行。

**前提条件**：当前在任务分支（非主干分支）

- AI 在 `docs/tasks/` 下查找含 `task-state.md` 的目录，读取任务状态和文档索引
- 若找不到：提示先执行 create-task
- 若找到多个：报错，要求用户手动确认
- 上下文仅在当前 session 内有效；新 session 开始时需重新执行 start-task
- 切换任务：切换 Git 分支后，在新 session 中执行 start-task 即可

### 3.3 任务内工作（自然语言子命令）

在任务工作模式下，用户以自然语言驱动以下操作：

- **需求**：规划 / 刷新 / 变更需求文档
- **设计**：规划 / 刷新 / 变更设计文档（含步骤划分）
- **实现**：开始实现当前步骤
- **提交**：按规范格式生成 commit message，与 `task-state.md` 记录对应
- **状态查询**：查询当前进展（当前阶段、当前步骤、遗留问题）
- **状态更新**：记录文件状态变更（如拆分了文件）、当前步骤变更
- **变更审查**：查询当前分支中哪些变更不属于本任务，评估其影响

### 3.4 验收

验收分为两个级别：

**步骤级别**：每个步骤完成后执行，包括自动化测试和必要的人工验收。部分步骤的验收是临时性的，会被后续步骤覆盖。

**任务整体级别**：所有步骤完成后执行，运行当前所有有效测试用例，并执行必要的人工验收。

验收由自然语言命令触发，结果记录到 `task-state.md`。

### 3.5 完成任务（complete-task）

**前提**：工作区干净（无任何未提交变更），防止任务文档在未提交状态下被误删。

**核对**（AI 执行，结果展示给用户，有问题则终止）：
1. 所有步骤均已标记完成且有对应提交
2. 所有验收标准（自动化 + 人工）均已通过；如有未通过项，列出并提示用户先执行验收

**操作**（每步需用户显式确认后执行）：
1. 删除整个任务目录（含所有文档及子目录）并提交
2. 创建 PR

> 若 PR review 后需返工，可通过 `git checkout <删除前的 commit> -- docs/tasks/<任务目录>/` 从 git 历史找回文档。

---

## 四、约束

- **一分支一任务**：每个 Git 分支同时只有一个 Task
- **一任务一 PR**：所有任务相关工作在同一 PR 中交付
- **过程文档**：任务文档 PR 合并前删除，不保留到仓库历史；如需保留设计理念，应合并入架构文档
- **步骤不合并**：多个步骤不允许合并在同一 commit 中提交
- **验收标准必须通过**：不保证零缺陷，但验收标准是交付底线

---

## 五、文档规范

### 拆分规则

需求文档和设计文档支持拆分（含子目录），以应对复杂任务：
- 需求类：以 `requirements-` 为前缀（默认文档 `requirements.md` 是特例）
- 设计类：以 `design-` 为前缀（默认文档 `design.md` 是特例）
- 拆分后原默认文档不再保留；所有文档均记录在 `task-state.md` 中

拆分后的文档层次由 AI 推断（通过读取标题和内容），结果更新到 `task-state.md` 的文档索引，用户可确认或修正。

### 模板

- 需求模板、设计模板：按任务类型分别设计（Feature vs Refactor 各一套）
- `task-state.md` 模板：通用，不按类型区分，包含文档索引区块
- 提交记录规范：严格格式，与 `task-state.md` 记录相互印证

---

## 六、设计原则

- **显式阶段**：三个阶段明确区分，但允许迭代回退
- **文档即过程**：任务文档是执行过程的产物，不是交付物，完成即销毁
- **提交记录为准**：`task-state.md` 反映当前状态，提交记录是最终真相

---

## 七、词汇表

AI 在处理自然语言指令时，需识别以下中英文对照关系：

| 英文            | 中文                    | 说明                             |
| --------------- | ----------------------- | -------------------------------- |
| Task            | 任务                    | 功能名称，两者完全等价           |
| create-task     | 创建任务                | 初始化新的 Task 事务             |
| start-task      | 开始任务 / 进入任务模式 | 建立任务上下文（与 resume 等价） |
| resume-task     | 恢复任务                | start-task 的别名                |
| complete-task   | 完成任务                | 完成核对、清理文档、创建 PR      |
| task-state.md   | 任务状态文件            | 文档列表与进展的单一来源         |
