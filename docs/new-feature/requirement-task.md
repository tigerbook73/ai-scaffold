# Task 管理系统 — 需求

## 一、核心概念

**Task** 是一个中等规模或复杂度的任务，通常需要数小时至数天才能完成，以一个 PR 为单位交付。

当前支持的 Task 类型：

- 特性（Feature）
- 重构（Refactor）

---

### 三个阶段

每个 Task 分为三个阶段，阶段之间可以有迭代（非严格线性）。

#### 1. 需求识别

明确任务的目标是什么（相对"黑盒"，关注 What）。

需求内容与任务类型相关，以 Feature 为例，内容可以包括：

- 功能需求
- 非功能需求
- 架构变更要求（需求引入的变更）
- 核心约束
- 验收标准（如何验证）

#### 2. 设计

明确如何实现需求（关注 How）。

设计内容包括：

- 核心架构设计
- 技术选型
- 关键模式设计
- 文件变更清单
- 测试方案
- **步骤划分**：每个步骤变动不能过大，要能被合理理解和 review。每个步骤通常对应一个 commit，也可以跨多个 commit，但不允许多个步骤合并在同一个 commit 中提交。

#### 3. 实现

根据设计的步骤划分，逐步实现、逐步提交，全部提交在独立的 Task 分支中。

---

### 阶段迭代说明

三个阶段并非完全线性：

- 设计过程中可能发现需求需要调整
- 实现过程中可能发现设计或需求不合理，需要变更

代价越往后越大，因此鼓励在前期尽量把事情做清楚。

---

## 二、任务管理规则

### 交付标准

- 所有任务相关工作在一个 PR 中完成
- 任务完成时，相关测试和验收均已通过（包括自动化测试和人工验证）
- 不能完全保证零遗留缺陷，但验收标准必须通过

### 文档生命周期

- 需求、设计、进展文档均为**过程文档**，任务完成后销毁
- PR 合并前，需删除所有 Task 相关文档
- 如需保留核心设计理念或功能描述，应合并入整体架构文档（不在本系统设计范围内）

### 进展跟踪

- 全程维护以下文档（任务完成前持续更新）：
  - `requirements.md`：需求（可拆分，见下）
  - `design.md`：设计（可拆分，见下）
  - `task-state.md`：任务状态与文档索引（主跟踪文档）
- `task-state.md` 是文档列表的单一来源，记录当前任务目录下所有文档的名称与用途
- 可通过 `task-state.md` 快速了解当前进展，但提交记录是兜底依据，代表真实已提交的进展（不含未提交内容）

### 文档拆分规则

需求文档和设计文档均支持拆分（甚至支持子目录），以应对复杂任务：

**需求文档拆分示例：**

- `requirements.md`：需求概述与核心需求（默认文档，简单任务只需此文件）
- `requirements-outline.md`：需求概述与文档组织说明
- `requirements-<topic>.md`：某一具体需求领域的描述与验收标准

**设计文档拆分示例：**

- `design.md`：设计概述与核心设计（默认文档，简单任务只需此文件）
- `design-outline.md`：设计概述与文档组织说明
- `design-<topic>.md`：某一具体设计领域的详细描述

所有拆分后的文档名称及用途，统一记录在 `task-state.md` 中。

### 步骤与提交

- Task 可根据大小划分为多个步骤
- 每个步骤通常对应一个 commit（可以跨多个 commit，但不允许多个步骤合并在同一个 commit 中），且可以单独测试和验证
- 若某步骤实现量较大（如一天内无法完成），可临时提交，但需在提交注释和 `task-state.md` 中说明

## 三、技能（Skills）规划

### 1. 创建任务（create-task）

- 创建新的 Git 分支
- 在 `docs/tasks/` 下以任务名称创建子目录（kebab-case 命名，如 `user-auth-flow`），并初始化三个文件：
  - `requirements.md`（初始可为空）
  - `design.md`（初始可为空）
  - `task-state.md`（初始包含一条创建记录，以及当前文档列表）
- 输入：任务名称、任务类型
- 前提条件：
  - 工作区必须干净（无未提交变更、无新文件）
  - `docs/tasks/` 目录下不存在任何已有任务目录

### 2. 开始任务（start-task / resume-task）

- 作用：进入任务工作模式，建立当前 session 的任务上下文
- 不需要参数，AI 在 `docs/tasks/` 下查找含有 `task-state.md` 的目录作为当前任务目录；同一分支下只存在一个任务目录
- AI 读取 `task-state.md`（含文档索引）及其他任务文档，在当前 session 中建立任务上下文（任务名称、类型、当前状态、当前步骤等）
- 上下文仅在当前 session 内有效；新 session 开始时需要重新执行 start-task
- 后续的自然语言指令默认针对当前任务执行
  - 例：说"规划需求" → AI 知道是在规划当前任务的需求，并写入 `requirements.md`
- 切换任务时，切换 Git 分支后在新 session 中执行 start-task 即可

> **注**：create-task 完成后会自动在当前 session 执行 start-task，无需手动触发。

### 3. 完成任务（complete-task）

- 前提条件：工作区必须干净（所有任务文档均已提交），防止未提交内容被误删
- AI 对比 `design.md`（及拆分文档）中的步骤与 `task-state.md` 中的完成记录，确认所有步骤均已标记完成且有对应提交
- 检查 `task-state.md` 中所有验收标准（自动化测试 + 人工验证）均已通过；如有未通过项，列出并提示用户先执行验收
- 验收全部通过后，需用户逐步确认以下操作再执行：
  1. 删除任务目录下所有文档并提交
  2. 创建 PR
- 提示：若 PR review 不通过需要返工，可通过 `git checkout <删除前的 commit> -- docs/tasks/<任务目录>/` 从 git 历史找回文档

### 4. 任务内子命令（在 start-task 状态下）

用户以自然语言交互，包括但不限于：

- 规划需求文档 / 刷新需求文档 / 按条件变更需求文档
- 规划设计文档 / 刷新设计文档 / 变更设计文档
- 开始实现当前步骤
- 查询当前状态（进行到哪一步、有哪些遗留问题）
- 更新当前状态（记录：文件状态变更--如拆分了文件，当前步骤变更）
- 提交：按特定格式生成提交注释，与 `task-state.md` 记录对应

另外，用户可以主动查询当前分支中哪些变更不属于本任务（如从主干同步的变更或顺手修复的 bug），以及这些变更是否会对本任务产生影响。

---

## 四、模板

1. **需求模板** 和 **设计模板**：按任务类型分别设计（Feature vs Refactor，两类模板不同）；拆分文档有对应的子模板
2. **task-state.md 模板**：通用设计，不按任务类型区分；包含文档索引区块
3. **提交记录规范**：需要严格的格式规范（在提交过程中执行），并需要尽量与 `task-state.md` 记录匹配，能够相互印证

---

## 五、验收机制

### 步骤级别验收

- 每个步骤完成后进行验收，包括：
  - 自动化测试（如单元测试、集成测试）
  - 人工验收（如需要）
- 有些步骤的验收是临时性的，后续步骤完成后会被覆盖或替代

### 任务整体级别验收

- 所有步骤完成后进行整体验收
- 运行所有当前仍有效的测试用例（涵盖未被后续步骤覆盖的步骤验收）
- 再执行必要的人工验收用例

### 验收执行规则

- 验收通过自然语言命令触发（以用户实际命令为准），执行自动化测试并确认人工验收结果
- 所有验收结果直接更新到 `task-state.md`，作为状态的单一来源
