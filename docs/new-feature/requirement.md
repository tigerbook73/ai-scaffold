# Task 管理系统 — 需求概述

## 一、核心概念

**Task** 是一个中等规模或复杂度的任务，通常需要数小时至数天才能完成，以一个 PR 为单位交付。

当前支持的 Task 类型：

- 特性（Feature）
- 重构（Refactoring）

---

### 三个阶段

每个 Task 分为三个阶段，阶段之间可以有迭代（非严格线性）。

#### 1. 需求识别

明确任务的目标是什么（相对"黑盒"，关注 What）。

需求内容与任务类型相关，以 Feature 为例，内容可以包括：

- 功能需求
- 非功能需求
- 架构变更要求（需求引入的变更）
- 核心约束
- 验收标准（如何验证）

#### 2. 设计

明确如何实现需求（关注 How）。

设计内容包括：

- 核心架构设计
- 技术选型
- 关键模式设计
- 文件变更清单
- 测试方案
- **步骤划分**：每个步骤变动不能过大，要能被合理理解和 review。每个步骤通常对应一个 commit，也可以跨多个 commit，但不允许多个步骤合并在同一个 commit 中提交。

#### 3. 实现

根据设计的步骤划分，逐步实现、逐步提交，全部提交在独立的 Task 分支中。

---

### 阶段迭代说明

三个阶段并非完全线性：

- 设计过程中可能发现需求需要调整
- 实现过程中可能发现设计或需求不合理，需要变更

代价越往后越大，因此鼓励在前期尽量把事情做清楚。

---

## 二、任务管理规则

### 交付标准

- 所有任务相关工作在一个 PR 中完成
- 任务完成时，相关测试和验收均已通过（包括自动化测试和人工验证）
- 不能完全保证零遗留缺陷，但验收标准必须通过

### 文档生命周期

- 需求、设计、实现均为**过程文档**，任务完成后销毁
- PR 合并前，需删除所有 Task 相关文档
- 如需保留核心设计理念或功能描述，应合并入整体架构文档（不在本系统设计范围内）

### 进展跟踪

- 全程维护需求、设计、实现文档（任务完成前持续更新）
- 单独维护 **PROGRESS.md**，记录当前状态
- 可通过进展文档快速了解当前进展（比直接看提交记录更快），但提交记录是兜底依据，代表真实已提交的进展（不含未提交内容）

### 步骤与提交

- Task 可根据大小划分为多个步骤
- 每个步骤通常对应一个 commit（可以跨多个 commit，但不允许多个步骤合并在同一个 commit 中），且可以单独测试和验证
- 若某步骤实现量较大（如一天内无法完成），可临时提交，但需在提交注释和 PROGRESS.md 中说明

## 三、技能（Skills）规划

### 1. 创建任务（create-task）

- 创建新的 Git 分支
- 在 `docs/tasks/` 目录下创建任务目录，并初始化三个文件：
  - `REQUIREMENTS.md`（初始可为空）
  - `DESIGN.md`（初始可为空）
  - `PROGRESS.md`（初始包含一条创建记录）
- 输入：任务名称、任务类型
- 前提条件：工作区必须干净（无未提交变更、无新文件）

### 2. 关闭任务（close-task）

- 前提条件：工作区必须干净（所有任务文档均已提交），防止未提交内容被误删
- AI 对比 DESIGN.md 中的步骤与 PROGRESS.md 中的完成记录，确认所有步骤均已标记完成且有对应提交
- 自动执行自动化测试步骤，确认测试通过
- 要求用户逐项确认人工验收步骤是否完成
- 验收全部通过后，自动删除任务目录下的所有文档（REQUIREMENTS.md / DESIGN.md / PROGRESS.md）并提交，同时清除 memory 中当前分支的任务状态
- 若 PR review 不通过需要返工，可通过 `git checkout <删除前的 commit> -- docs/tasks/<任务目录>/` 从 git 历史找回文档

### 3. 开始任务（start-task）

- 作用：进入任务工作模式
- 不需要参数，AI 根据当前 Git 分支自动定位任务目录（一个分支对应一个任务）
- AI 读取任务目录下的文档，将任务相关信息（任务名称、类型、当前状态、当前步骤等）写入 memory，以当前分支名为 key，实现跨 session 保持任务上下文
- 支持并行任务：memory 中按分支名存储各自的任务状态，切换分支后执行 start-task 即可切换任务上下文
- 后续的自然语言指令默认针对当前任务执行
  - 例：说"规划需求" → AI 知道是在规划当前任务的需求，并写入 `REQUIREMENTS.md`

### 4. 暂停任务（pause-task）

- 作用：退出任务工作模式
- 清除 memory 中当前分支对应的任务状态

### 5. 任务内子命令（在 start-task 状态下）

包括但不限于：

- 规划需求文档 / 刷新需求文档 / 按条件变更需求文档
- 规划设计文档 / 刷新设计文档 / 变更设计文档
- 开始实现当前步骤
- 查询当前状态（进行到哪一步、有哪些遗留问题）
- 提交：按特定格式生成提交注释，与 PROGRESS.md 记录对应

另外，用户可以主动查询当前分支中哪些变更不属于本任务（如从主干同步的变更或顺手修复的 bug），以及这些变更是否会对本任务产生影响。

---

## 四、模板

1. **需求模板** 和 **设计模板**：按任务类型分别设计（特性 vs 重构，两类模板不同）
2. **进展文档模板**：通用设计，不按任务类型区分
3. **提交记录规范**：需要严格的格式规范（在提交过程中执行），并需要尽量与进展文档匹配，能够相互印证

---

## 五、验收机制

### 步骤级别验收

- 每个步骤完成后进行验收，包括：
  - 自动化测试（如单元测试、集成测试）
  - 人工验收（如需要）
- 有些步骤的验收是临时性的，后续步骤完成后会被覆盖或替代

### 任务整体级别验收

- 所有步骤完成后进行整体验收
- 运行所有当前仍有效的测试用例（涵盖未被后续步骤覆盖的步骤验收）
- 再执行必要的人工验收用例

---

## 六、Review 功能

### 设计目标

提供工具对当前正在进行或已完成的步骤变更进行 review。

最优场景：对**即将完成的步骤**进行 review，好处是可以直接在 IDE 中看到变更内容。

### Review 工具行为

- AI 分析变更内容并分组展示；默认对当前 working tree（未提交变更）进行 review，也支持指定 commit 或 commit range 对已提交步骤进行 review
- 按变更分组逐一说明：每组变更了哪些文件、为什么这样变更、目的是什么
- 不需要对所有变更都详细说明，语法格式变更、注释增加等可以略过
- 支持中途打断和继续
- 支持查询"当前 review 到第几步"
- Review 进度记录在 memory 中（不放入 repo），粒度为步骤编号即可

### Review 指令

- **开始 review（start-review）**：启动 review 流程，从 memory 中读取当前进度并继续；若无进度记录则从第一步开始
- **结束 review（end-review）**：退出 review 模式，将当前步骤位置写入 memory，供下次快速恢复

### 扩展用途

Review 功能也可用于**学习技术**，不限于任务 review，可以对任意变更进行讲解。
