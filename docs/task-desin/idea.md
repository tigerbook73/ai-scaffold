# Task 管理系统 — 需求概述

## 一、核心概念

**Task** 是一个中等规模或复杂度的任务，通常需要数小时至数天才能完成，以一个 PR 为单位交付。

当前支持的 Task 类型：

- 特性（Feature）
- 重构（Refactoring）

---

### 三个阶段

每个 Task 分为三个阶段，阶段之间可以有迭代（非严格线性）。

#### 1. 需求识别

明确任务的目标是什么（相对"黑盒"，关注 What）。

跟我需求的内容和需求和任务类型相关,以feature为例,内容可以包括：

- 功能需求
- 非功能需求
- 架构变更要求（需求引入的变更）
- 核心约束
- 验收标准（如何验证）

#### 2. 设计

明确如何实现需求（关注 How）。

设计内容包括：

- 核心架构设计
- 技术选型
- 关键模式设计
- 文件变更清单
- 测试方案
- **步骤划分**：每个步骤变动不能过大，要能被合理理解和 review，每个步骤通常是一个commit 当然也可以跨多个commit，但不允许多个步骤在同一个commit中提交。

#### 3. 实现

根据设计的步骤划分，逐步实现、逐步提交，全部提交在独立的 Task 分支中。

---

### 阶段迭代说明

三个阶段并非完全线性：

- 设计过程中可能发现需求需要调整
- 实现过程中可能发现设计或需求不合理，需要变更

代价越往后越大，因此鼓励在前期尽量把事情做清楚。

---

## 二、任务管理规则

### 交付标准

- 所有任务相关工作在一个 PR 中完成
- 任务完成时，相关测试和验收均已通过（包括自动化测试和人工验证）
- 不能完全保证零遗留缺陷，但验收标准必须通过

### 文档生命周期

- 需求、设计、实现均为**过程文档**，任务完成后销毁
- PR 合并前，需删除所有 Task 相关文档
- 如需保留核心设计理念或功能描述，应合并入整体架构文档（不在本系统设计范围内）

### 进展跟踪

- 全程维护需求、设计、实现文档（任务完成前持续更新）
- 单独维护 **PROGRESS.md**，记录当前状态
- 可通过进展文档快速了解当前进展（比直接看提交记录更快），但需要有提交记录兜底，提交记录才代表真实的已经提交的进展（不含未提交的内容）

### 步骤与提交

- Task 可根据大小划分为多个步骤
- 原则上每个步骤是一个独立提交单位，可以单独测试/验证
- 若某步骤实现量较大（如一天内无法完成），可临时提交，但需在提交注释和 PROGRESS.md 中说明

## 三、技能（Skills）规划

### 1. 创建任务（create-task）

- 创建新的 Git 分支
- 在 `docs/task/` 目录下创建任务目录，并初始化三个文件：
  - `REQUIREMENTS.md`（初始可为空）
  - `DESIGN.md`（初始可为空）
  - `PROGRESS.md`（初始包含一条创建记录）
- 输入：任务名称、任务类型
- 创建任务的时候工作区必须是干净的，没有文件变更，没有新文件，没有待提交变更

### 2. 关闭任务（close-task）

- 检查需求和设计是否全部有对应的提交记录
- 确认自动化测试已通过
- 确认人工验证已完成（需要人为确认）
- 验收粒度分为：步骤级别 和 任务整体级别

### 3. 开始任务（start-task）

- 作用：告知 AI 当前进入任务工作模式
- AI 加载任务相关的进展文档和技能上下文
- 后续的自然语言指令默认针对当前任务执行
  - 例：说"规划需求" → AI 知道是在规划当前任务的需求，并写入 `REQUIREMENTS.md`

### 4. 暂停任务（pause-task）

- 作用：退出任务工作模式
- AI 可释放任务相关上下文（是否能释放取决于 AI 自身能力）

### 5. 任务内子命令（在 start-task 状态下）

包括但不限于：

- 规划需求文档 / 刷新需求文档 / 按条件变更需求文档
- 规划设计文档 / 刷新设计文档 / 变更设计文档
- 开始实现当前步骤
- 查询当前状态（进行到哪一步、有哪些遗留问题）
- 提交：按特定格式生成提交注释，与 PROGRESS.md 记录对应

另外如果在任务中做了一些其他变更和本任务不相关的变更（如从主干分支同步过来的变更或修订了一些bug），这时候可能需要提醒一下开发者这些变更是否和本任务相关。如果能够主动提及最好如果不能够主动提及那么呃可以由用户主动发起：如查看一下历史记录哪些变更不是由本任务发起的是否会对本任务产生影响等。

---

## 四、模板

1. **需求模板** 和 **设计模板**：按任务类型分别设计（特性 vs 重构，两类模板不同）
2. **进展文档模板**：通用设计，不按任务类型区分
3. **提交记录规范**：需要严格的格式规范（在提交过程中执行），并需要尽量和进展文档匹配能够相互印证。

---

## 五、Review 功能

### 设计目标

提供工具对当前正在进行或已完成的步骤变更进行 review。

最优场景：对**即将完成的步骤**进行 review，好处是可以直接在 IDE 中看到变更内容。

### Review 工具行为

- AI 根据某一设计步骤的变更内容，分组展示
- 逐步说明：每步变更了哪些文件、为什么这样变更、目的是什么
- 支持中途打断和继续
- 支持查询"当前 review 到第几步"
- Review 进度需要记录（粒度：步骤编号即可）

呃不用对所有变更都详细说明比如说一些语法格式的变更啊注释增加啊这些可以不用说。

### Review 指令

- **开始 review（start-review）**：启动 review 流程，识别当前进度并继续
- **结束 review（end-review）**：退出 review 模式，AI 可释放相关上下文，但当前步骤位置需保留，供下次快速恢复。 review的进展记录不是那么重要，不用放在repo仓库中，可以考虑放在memory中。

### 扩展用途

Review 功能也可用于**学习技术**，不限于任务 review。用于对变更进行讲解。
