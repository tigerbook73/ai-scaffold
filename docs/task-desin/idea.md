# task相关的skill

# 先描述的核心概念

一个task是一个中等规模或复杂度的任务，需要较长时间如数个小时或者数天才能完成工作，通常是在一个PR中完成。
Task可以是多种类型目前支持的包括特性和重构。

每个task可以分为需求识别设计和实现三个阶段（可以有迭代）

- 需求识别主要是识别这个任务的目标是做什，相对来说有点黑盒的概念但呃也不完全是黑河这个是相对的：
  - 需求部分可以包括功能需求、架构要求的变更、重构的诉求、以及很重要的如何验证
- 设计的部分就包括如何实现这个上面的需求
  - 包含架构的核心设计、技术的选型、使用的关键模式设计、的文件变更以及如何测试，最关键的是要能够划分出合理的步骤每一个步骤不能太大变动太大人能够去合理的理解、review。
- 实现部分的话相对就明确了,就是根据设计前面设计步骤的划分，然后逐步实现、逐步提交，当然都是提交在单独的task分支里

上述三个部分并不是完全线性的。有可能在设计的过程中发现需求可能要调整有可能在。也有可能在呃，实践的过程中发现有些设计或者甚至需求不太合理，需要调整。当然，如果要调整的话，代价通常会比较大，所以我们希望会有尽量在前面一步把事情完全做好。

# 任务的管理

所有任务相关的需求设计实现都是在一个PR中完成的,呃，这里不是说，呃，任务完成后就不能有缺陷，但至少任务完成以后，相关的测试验收都是通过的，是否还有遗留缺陷？那么这个是无法完全保证的。

任务相关的需求设计实现都是过程文档。在任务完成后，都需要销毁。所以在PR前是要把任务相关的内容，全部删除掉。如果要保留核心相关的设计理念功能需求的描述，那么需要把特性和核心的设计合并到整体的架构文档中。这部分内容不在本文的设计范围之内。

总体的任务的管理是按需求设计实现大的此步骤。但是中间可以有反复，在这个任务没有完成前，需求设计和实现文档都是要有维护的。并且有。进展文档，记录当前的状态。可以通过看进展文档大致了解当前进行到哪一步了呃，当然，最保险的措施是看。提交的记录但是通过看进展文档可以很快的确认状态比每次都比较的话要快一点。

任务的话，可以根据大小划分成不同步骤。前面也说过了呃，一般来说，每个步骤是一个独立的提交单位。当然这个不是一个严格的要求每次是可以如果有一些特性如果不是特性有些步骤如果实现的设计的比较大呃一天之内没法完成没法单独提交也可以临时先提交啊只要在注释里面说明在步骤里面记录就好。

对于任务的管理我初步规划有以下相关的技能

1. 创建任务：呃我的理解应该是创建一个新的分支并且创建相关的空的目录结构，在docs/task目录下，创建三个文件，REQUIREMENT.md / DESIGN.md / PROGRESS.md 。 这时候可以只有一个任务的名称，呃其中requirement, design可以基本上是空的，但是progress的话是有内容的有一条记录。
2. 关闭任务： 关闭任务的话就是检查任务中的呃需求设计是否全部都实现有对应提交记录，并且验收和测试都已通过包括自动化测试和人工验证，人工验证需要人为确认。呃验证和验收有步骤及和整个任务级别。应该是不一样的。
3. 开始任务： 呃，开始任务是为了AI的，呃，当前上下文设计主要是目的告诉。 AI，我当前要开始进行任务相关的工作了？这时候AI就可以把任务相关的。进展啊，技能啊，加载进来。后面，我说一些关于我的一些指令啊，都应该是和。通过自然语言说明但是呢，呃，希望AI能够知道我是对这个任务。当前的任务进行执行的。比如说任务已经开始以后，我说规划需求。那么他就知道我现在是希望规划这个任务的需求。需求文档是需要写在最硬的requirement点MD文档。
4. 暂停任务：暂停任务呢，是针对开始任务来说的就是说啊，我现在不再继续处理任务了。你可以忘记一些当时任务相关的上下文至于是否能够忘记这个取决于AI自己。
5. 在开始任务的状态下，我可以发出一些子命令，包括但不限于:

- 规划，需求文档。刷新需求文档。更改需求文档根据什么什么什么条件
- 规划刷新，变更设计文档。
- 开始设计文档，实现。
- 当前我现在处于什么状态？做到哪一步，有什么遗留问题？
- 提交，提交的时候自动按照特定的格式进行注释这样的话呃能够和progress文档中的记录很容易的对应起。

关于模板：

1. 需求和设计有单独的模板，而且模板是针对不同类型的任务，目前目前考虑的话是特性和重构，这两类的模板是不同的。
2. 进展文档可以考虑通用设计不一定限于啊这个按照类型来分只要能够做到就可
3. 关于提交记录呃需要有严格的规范至少是在提交过程中啊前面也提到

关于review：
为了能够更方便地检视变更，
一是前面提到的呃前面提到的每次提交不能内容太长，
二是需要提供工具对当前正在进行的或者是已经完成的嗯变更进行review。最好是对当前即将完成的步骤进行review，好处是可以从IDE框架中直接看到变更内容。

关于review的工具初步考虑是这样的，要求AI根据某一次设计的步骤的变更内容把它分组进行展示然后进行分组安不走进行一步一步的说明每部都说明这次这个步骤里面变更了哪些文件文件中为什么要这么变更目的是啥。解释过程中仍可以打断并且可以继续然后下次如果没有检视完的话还可以问我现在解释到什么地步所以这个reviewed步骤也是需要记录下来的。对于review的话可以用开始review、结束review，这样的指令开始review表明要开始启动review要识别出当前review到什么地步然后呢呃需要把当前的步骤记下来然后在这个过程中可能需要识别人为的一些呃指令。结束礼服呢就可以把一些命令记下来而忘记但是当前的步骤希望还是能够记下下次我可以快速地回到当前的状态当然这个步骤就不用记的这么细了只要知道第几步就可以了。
