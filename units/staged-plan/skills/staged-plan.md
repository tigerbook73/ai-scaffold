# staged-plan

把"先规划后实现"变成一套可操作、可恢复、可追溯的流程。核心思想不是维护一份始终正确的文档，而是**记录完整的决策和变更轨迹**——文档在某个时间点可能不再完整，但轨迹始终准确，任何人都能沿轨迹还原当前状态是怎么来的。

在开始实现一个有一定规模的 feature 之前用于规划，以及在实现过程中管理变更和进度。当用户提出"规划/设计一个feature"、"先讨论需求和架构"、"这个feature比较大需要分阶段"、"继续上次没做完的设计"、"进入下一步骤"、"发现前面的设计有问题"、"看一下当前规划进度"、"这步实现完了，接下来怎么做"等诉求时使用，即使用户没有明确说"用规划skill"也应主动触发。

## 文件结构

所有产出放在 `plans/<feature-slug>/` 下：

```
plans/<feature-slug>/
├── PROGRESS.md          # 当前阶段、步骤状态、下一步建议 —— 每次开始/结束工作都必须读写
├── DECISIONS.md         # 横切性全局约束清单，打了[arch]标记的条目最终归并到架构指导文档
├── 00-brief.md          # 需求（behavior层面）+ 架构 + 核心技术选型
├── step-map.md          # 步骤地图：有序的功能切片列表，每步带验证方式和变更记录
├── requirements/        # 可选，仅当需求本身规模很大时才拆分（见 ~/.claude/skills/aisk-staged-plan/resources/references/splitting-guide.md）
└── design/              # 可选，设计章节文件（见 ~/.claude/skills/aisk-staged-plan/resources/references/splitting-guide.md）
```

模板在 `~/.claude/skills/aisk-staged-plan/resources/assets/` 下，新建对应文件时先读对应模板文件，以其结构创建，不要从空白发明结构。

## 四层流程

### 第一层：需求文档（behavior only，不写 presentation）

需求文档只回答"用户能做什么、系统响应什么"，不写"界面怎么长、用什么组件"。这条边界是需求文档保持稳定的根本原因：行为比实现方式稳定得多。

判断一句话该不该进需求文档：

- ✅ "用户可以按日期范围筛选订单" → 行为，进需求文档
- ❌ "用日历组件还是两个输入框" → 呈现方式，进设计
- ❌ "筛选结果要在 200ms 内返回" → 非功能性约束，进需求文档的约束章节

对于"一开始想不清楚的 UI 细节"：单独维护一份 `design/ui-pending.md` 草稿，不混进需求文档，设计阶段确定后直接写进对应设计章节。不要让不确定的内容污染本来应该稳定的需求文档。

需求文档、步骤地图是否拆分，读 `~/.claude/skills/aisk-staged-plan/resources/references/splitting-guide.md` 判断（默认不拆）。如拆出了 `design/` 章节，各章节的细化流程读 `~/.claude/skills/aisk-staged-plan/resources/references/chapter-loop-guide.md`。

### 第二层：架构与关键决策（独立文档）

把"跨功能模块的约束性决定"从需求和设计里分离出来，放进 `DECISIONS.md`。判断标准：这个决定是否会约束多个后续步骤或多个设计章节？是则进 `DECISIONS.md`，否则留在对应章节里。

每条决策条目格式：

```
- [决定内容]（来源：章节/步骤 N，理由：……）
  [arch] ← 如果这条决定通用性足够强、适用范围超出本 feature，打此标记，feature 结束时归并到架构指导文档
```

`[arch]` 标记要当场打，不要等 feature 做完再回来翻——feature 结束时的归并动作，就是收集所有打了标记的条目，而不是从零回忆。

### 第三层：步骤地图（轻量设计，行动导向）

不是描述性设计文档，是一张"做什么 → 怎么验证"的有序列表。规划前读 `~/.claude/skills/aisk-staged-plan/resources/references/step-map-guide.md`。概要：

**步骤粒度标准**：每个步骤是一个可独立验证的功能切片——做完这步，有一件具体的事可以跑通。不要按"修改了哪些文件"切，要按"完成了什么可观察的功能"切。

**步骤格式**：

```
### Step N: [步骤名称]
目标：做完这步，XX 功能可以 [具体行为]。
验证：
- 功能验证：[命令 / 操作路径，必填]
- 自动化测试：[新增/修改的核心逻辑需有对应测试；如无，说明原因]
依赖：Step M（需要 M 完成后才能做）
状态：待开始 / 进行中 / 完成 / 已修正（见 Amendment）

[Amendment - 仅在修正型变更时添加]
原决定：……
修正为：……
原因：……
影响范围：已完成的 Step X 需要补丁（见 Step N+k）/ 不影响已完成步骤
```

步骤地图在设计阶段只写到"知道每步大概做什么、知道怎么验证"的粒度，不要提前猜实现细节。每个步骤的具体实现，在轮到它的时候再就地细化。

### 第四层：逐步实现（就地细化 + 变更处理）

每个步骤的处理遵循同一个循环：

**开始前**：

1. 读 `PROGRESS.md` 确认当前步骤
2. 读 `00-brief.md` + `DECISIONS.md` + 本步骤依赖的已完成步骤的实现结果（不是文档摘要，是实际产出）
3. 就地细化：把这个步骤展开成具体的实现任务，这时才涉及"改哪些文件、怎么改"
4. 列出本步骤的实现计划（关键决定 + 改动范围），等待用户确认后再开始 coding。
   用户可以说"直接做"或开启 auto 模式跳过确认。

**完成标准（不是"功能跑起来了"就打钩）**：

1. ✅ 验证方式通过
2. ✅ 做了前瞻性检查："下一步能在这个实现上干净地继续吗？有没有我现在已经能预见到会妨碍下一步的地方？"

前瞻性检查是主动把"下一步才会暴露的问题"提前发现，成本远低于被动暴露后的修复。

**完成后**：更新 `PROGRESS.md`，如果产生了横切性决定，写进 `DECISIONS.md` 并判断是否打 `[arch]`。

## 变更处理（重要）

实现过程中遇到需要修改的情况，先判断类型，再按对应方式处理。遇到变更时读 `~/.claude/skills/aisk-staged-plan/resources/references/change-handling-guide.md`。这里是核心决策逻辑：

### 追加型变更（发现还需要多做一件事）

直接在步骤地图后面加新步骤，标注"基于 Step N 发现的新增需求"，继续推进。

### 修正型变更（前面的决定本身有问题）

**先做关键判断**：这个问题在后续步骤里会扩散，还是可以被隔离？

- **扩散型**（后续 N 个步骤都要在错误的基础上叠代码，N > 3 通常是信号）：
  停下来，当场修正，不要硬撑继续。操作：
  1. 在有问题的步骤加 Amendment 注记（原决定、修正为、原因、影响范围）
  2. 评估已完成步骤里有没有依赖这个决定的实现 → 有则在继续之前修复
  3. 修正完成后重新进入当前步骤

- **可隔离型**（只有一两个后续步骤会碰到，现有实现能支撑）：
  加 Amendment 注记，在步骤地图末尾加一个专门的重构步骤，继续推进功能实现，等功能跑通后再处理。

**不管哪种类型，都不删原来的步骤内容**——Amendment 是追加注记，不是覆盖，保持变更轨迹完整。

## 多 Session 支持

每次技能被触发时：

1. 先检查 `plans/<feature-slug>/PROGRESS.md` 是否存在：
   - 不存在 → 新 feature，从第一层开始，按 `~/.claude/skills/aisk-staged-plan/resources/assets/progress-template.md` 创建
   - 存在 → 读取并向用户复述：当前阶段、已完成步骤、当前进行中的步骤停在哪、建议下一步做什么

2. 任何实质性进展后，立刻更新 `PROGRESS.md`，不要攒到最后——步骤讨论到一半没有定论，也要记"停在哪个问题上"，不要假设下次 session 还记得。

3. 建议在每个步骤完成、或每次会话结束时提交 `plans/<feature-slug>/` 到 git，给进度文件一条可追溯的历史记录。

## Feature 完成

所有步骤完成后，执行以下收尾动作：

1. **跑完整自动化测试**：运行项目的全量自动化测试套件，而不只是本 feature 各步骤新增的测试——确保原有测试用例也不因本次改动失效。
2. **推荐轻量 review**：建议用户运行 `/code-review` 对本 feature 的改动做一次整体审查。
3. **归并架构文档**：检查 `DECISIONS.md` 里所有打了 `[arch]` 标记的条目，提醒用户归并到架构指导文档，并更新 `PROGRESS.md` 里的"架构归并待办"状态。
4. **清理过程文档**：提醒用户决定是否保留 `plans/<feature-slug>/`。通常可以删除或归档——规划文档的价值在过程中，代码合并后没有长期保留的必要；如需保留，建议移到专门的归档目录而非留在工作树中。

## 何时不需要这套流程

如果是小改动（bug 修复、孤立的小函数），不要套用三层文档流程，直接帮忙改就行。这套流程是为"有一定规模、值得先规划再动手"的 feature 准备的。

需求规模判断由 AI 根据场景给出建议，用户做最终决定。用户随时可以主动要求使用或不使用这套流程，AI 服从指令。
