# 步骤地图操作指南

## 步骤粒度：怎么切才对

步骤地图的核心判断是"每步切多大"。两个错误方向：

- **太大**："实现整个订单系统" → 细化它本身就是一轮完整规划，不是 just-in-time
- **太小**："给 users 表加一个 deleted_at 字段" → 步骤数量会爆炸，地图失去导航意义

**正确标准：每个步骤是一个可独立验证的功能切片。** 做完这步，有一件具体的事可以跑通——哪怕是局部的 e2e，不只是"完成了某个文件的修改"。

实用判断：能不能给这步写出一句"做完这步，用户/系统可以 [具体行为]"？可以的话粒度就对了。

步骤太大的信号：写不出一句具体的可观察行为，只能写"完成 XX 模块的开发"。
步骤太小的信号：验证方式是"看代码改对了没有"，而不是"跑一个命令或操作一下功能"。

## 设计阶段的步骤地图应该长什么样

设计阶段不要试图把每个步骤写到可以直接开始写代码的程度——那是就地细化阶段的事。设计阶段的步骤地图只需要：

- 能看出整体的推进顺序
- 知道每步完成后能验证什么
- 知道步骤之间的依赖关系（谁必须在谁之前完成）

示例（一个订单筛选功能的步骤地图，设计阶段的粒度）：

```markdown
### Step 1: 数据层 — 筛选查询

目标：按日期范围 + 状态筛选订单的查询可以跑通
验证：curl /api/orders?from=2024-01&to=2024-03&status=paid 返回正确的数据集
依赖：无
状态：待开始

### Step 2: API 层 — 筛选接口

目标：筛选接口按约定格式返回结果，含分页
验证：Postman/curl 覆盖边界情况（空结果、参数缺失、非法参数）全部返回预期
依赖：Step 1
状态：待开始

### Step 3: 前端 — 筛选 UI 接入

目标：用户在页面上操作筛选，结果正确刷新
验证：浏览器手动操作，覆盖筛选、清空、翻页三个路径
依赖：Step 2
状态：待开始
```

注意：这里没有写"改哪些文件"、"用什么 ORM 方法"——那些在就地细化时再展开。

## 就地细化：轮到某步时才展开细节

开始一个步骤时，在 `step-map.md` 的对应步骤下面展开细化内容（或者在单独的 scratch 区域），不要因为某步还没轮到就提前细化它——那时候的信息是不完整的，细化出来大概率要修正。

就地细化的输出物不需要写成文档——它可以直接是 Claude 和你的对话，最终落地到代码里。只需要把"影响后续步骤的决定"写进 `DECISIONS.md`，把"这步完成了"的状态写进 `PROGRESS.md`。

## 完成一个步骤的标准动作

```
1. 验证方式通过
2. 前瞻性检查：
   问自己/问 Claude："下一步（Step N+1）能在这个实现上干净地继续吗？
   有没有我现在能预见到、会妨碍下一步的地方？"
3. 如果前瞻性检查发现了问题 → 转到 ~/.claude/skills/aisk-staged-plan-staged-plan/resources/references/change-handling-guide.md
4. 如果没有问题 → 更新步骤状态为"完成"，更新 PROGRESS.md
```

前瞻性检查不需要很长时间，30 秒的快速问答就够。它的价值是把"下一步才暴露的问题"提前发现——主动发现比被动暴露的修复成本低得多。

## Amendment 格式

在被修正的步骤下面追加（不要修改原有内容）：

```markdown
[Amendment — Step M 实现时发现]
原决定：[原来准备怎么做]
修正为：[修正后的决定]
原因：[为什么原来的决定有问题]
影响范围：

- 已完成步骤：Step X 的 [具体部分] 需要补丁，见 Step N+k
- 后续步骤：Step Y 需要在细化时考虑这条修正
```

Amendment 是追加，不是覆盖。原始内容保留，完整变更轨迹可追溯。
