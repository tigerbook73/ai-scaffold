# 设计章节细化指南

这份文件在有独立设计章节（`design/` 下的文件）时使用。如果没有独立设计章节，设计决定直接通过 step-map.md 里的步骤就地细化，不需要这份文件。

## 开始细化某章节前

1. 读 `PROGRESS.md`，确认当前章节和它的 `depends_on`。
2. 完整读取：`00-brief.md`、`DECISIONS.md`，以及 `depends_on` 列出的每个章节文件的**全文**。不要转述成摘要——转述本身就是信息丢失的高发环节。
3. 如果章节文件还不存在，用 `.aisk/staged-plan/resources/chapter-template.md` 创建，填好 `depends_on` 和 `status: draft`。
4. 跟用户确认这一轮的边界："这一章只讨论 XX 范围，对吗？"——防止不知不觉漂移到其他章节。

## 讨论过程中

- 用户的关注点是"是什么 / 为什么这样决定"，不是逐行代码。除非用户主动要求，不要在设计章节里展开具体的文件改动清单——那是步骤就地细化时的事。
- 讨论中产生的对其他章节的关联，记下来但不展开："这个点放到 XX 章节再细化"。

## 章节收尾

1. 把决定、理由、未决问题写进章节文件。
2. 自检：对照 `00-brief.md`、`DECISIONS.md`、依赖章节，检查有没有冲突或遗漏，把自检结果列给用户，而不是要求用户自己比对全文。
3. 用户确认后：
   - `status` 改成 `final`
   - 产生了横切性约束的决定补进 `DECISIONS.md`，判断是否打 `[arch]` 标记
   - 更新 `PROGRESS.md`，标记完成，给出下一个建议处理的章节
4. 提示用户：这章已定稿写入文件，可以 `/clear` 再继续下一章，下次开始时会重新读取需要的文件。

## 中途暂停

不要等到章节"自然收尾"才写进文件——只要有实质性决定产生，即使章节还没定稿，也要把当前进展写进草稿和 `PROGRESS.md`（`status: draft`，注明"停在哪个问题上"）。下次 session 恢复时，一切以文件内容为准，不依赖对话记忆。
