# 变更处理指南

实现过程中遇到需要修改的情况，先判断类型，再按对应流程处理。

## 第一步：判断类型

**追加型**：发现了还需要多做的事情，原来的决定本身没有错。
→ 直接走追加流程。

**修正型**：前面某个决定本身有问题，继续按原决定做会产生错误或需要重构的代码。
→ 先判断"扩散还是隔离"，再走对应流程。

## 追加型流程

在 `step-map.md` 末尾加新步骤，标注"基于 Step N 实现时发现的新增需求"，继续推进。无需停下来，无需修改已有内容。

## 修正型流程

### 关键判断：扩散型 还是 可隔离型？

**问这个问题**：如果我继续按原决定推进，后续有多少个步骤会在这个有问题的基础上叠加代码？

**扩散型信号**（必须当场修）：

- 后续多个步骤都依赖这个有问题的决定（N > 3 通常是明确信号）
- 问题涉及核心数据结构、接口契约、或跨模块的假设——这类问题越晚改，代价越高，是指数级而不是线性的
- 继续推进意味着"明知道要重构还在堆代码"

**可隔离型信号**（可以继续推进，留技术债）：

- 只有一两个后续步骤会碰到这个问题
- 问题局限在某个模块内部，不会扩散到外部接口
- 现有实现能支撑后续步骤，只是不够优雅

### 扩散型：停下来修

```
1. 停止当前步骤的实现，不要在已知有问题的基础上继续堆代码。

2. 在 step-map.md 里找到有问题的那个步骤，添加 Amendment 注记：
   - 原决定是什么
   - 修正为什么
   - 为什么原来的不对
   - 影响范围（哪些已完成步骤受影响）

3. 检查已完成的步骤里，有没有依赖这个被修正决定的实现。
   → 有：在继续之前先修复这些实现，不要留着"等以后再说"。
     它们会成为每个后续步骤的隐患，越晚修代价越高。
   → 没有：直接进下一步。

4. 如果修正后的决定对其他步骤也有约束力，更新 DECISIONS.md。

5. 修正完成，重新进入当前步骤，继续实现。
```

**不要做的事**：明知道是扩散型问题，还是选择"先把当前步骤做完，以后再修"——"以后再修"几乎总是会变成整体重构，代价远高于现在停下来修。

### 可隔离型：记录技术债，继续推进

```
1. 在有问题的步骤里加 Amendment 注记，标明"可隔离，记为技术债"。

2. 在 step-map.md 末尾加一个专门的重构步骤，说明：
   - 要改什么（具体到实现层面）
   - 为什么留到最后（可隔离，不影响功能推进）
   - 做完这个步骤的验证方式

3. 继续推进当前功能实现，等功能跑通后再处理技术债步骤。
```

**不要做的事**：发现了可隔离的问题，当场随手改，但没有记录。下一个步骤细化时又"重新发现"同一个问题，来回浪费时间。

## 实现过程中发现前面设计有问题，但当前步骤还没做完

这是最常见的情况，判断依据同上（扩散 vs 可隔离）。

补充一个判断维度：**这个问题影响当前步骤能否做对，还是只影响后面某个步骤？**

- 影响当前步骤：不要硬撑着把当前步骤做完，先修正设计决定，再继续。
  做完一个你已经知道有问题的步骤，等于在已知错误的基础上做了验证，这个验证是无意义的。
- 只影响后面某步：把发现的问题记在那个步骤的细化提醒里（"细化这步时需要重新审视 X 决定"），
  当前步骤继续做完，下次轮到那步时这条提醒会在。

## 遇到需求修改（不只是设计/实现问题）

如果是**实现层面暴露了需求本身的问题**（不是"怎么实现"的问题，而是"要做什么"的问题），操作有所不同：

- **需求边界调整**（原来理解有偏差，要做的范围需要修正）：修改 `00-brief.md` 里对应的需求描述，标注"基于 Step N 实现时发现的调整"，同时评估已有步骤是否需要 Amendment。
- **发现了遗漏的用户行为**（追加需求）：在 `00-brief.md` 里追加（不改已有内容），在步骤地图里追加对应步骤。
- **只是 UI/实现细节的调整**（不是行为层面的变化）：直接在设计层面处理，不需要动 `00-brief.md`。
