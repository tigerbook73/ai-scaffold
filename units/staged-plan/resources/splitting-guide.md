# 拆分文档的判断标准

在第一层需求文档收尾时，以及在规划步骤地图前，用这份文件判断"要不要拆""拆到什么粒度"。

## 需求要不要单独拆出 requirements/

默认不拆，直接把需求写进 `00-brief.md` 的开头章节。满足下面任意一条才拆：

- 需求本身很复杂：多个相对独立的用户故事、大量边界情况、或者非功能性约束独立成章更清晰。
- 预期设计和实现阶段会多次迭代，需求部分需要作为"冻结的只读输入"来保护，防止被后续迭代误改。

拆分后：`00-brief.md` 开头仍然保留从 `requirements/00-overview.md` 提炼的摘要，不能只剩一个链接。设计和实现阶段都会带着 `00-brief.md` 走，如果它只剩链接，关键行为约束就在传递中丢失了。

**注意**：需求文档只记录 behavior（用户行为和系统响应），不记录 presentation（界面细节）。不确定的 UI 细节放 `design/ui-pending.md` 草稿，设计阶段再补充进对应章节，不要进需求文档。

## 步骤地图要不要拆出独立设计章节文件

步骤地图（`step-map.md`）是所有 feature 都需要的。独立的设计章节文件（`design/` 下的 `.md` 文件）是可选的，只在满足下面条件时才值得创建：

**值得创建独立设计章节的条件**：

- 某个技术领域（如数据库设计、API 契约、前端架构）需要在细化设计时经历多轮讨论循环，讨论的过程性内容值得独立追踪，不适合和步骤地图混在一起。
- 这个领域的设计决定会被多个步骤引用，作为独立文件更容易在细化对应步骤时带入。
- feature 预期跨多个 session，拆成独立文件配合 PROGRESS.md 才能作为清晰的恢复点。

**不值得创建独立设计章节的情况**：

- 设计细节可以直接在步骤地图的各步骤就地展开
- feature 规模不大，一两次 session 能做完
- 设计决定已经在 DECISIONS.md 里覆盖了，没有需要独立追踪的讨论过程

## 拆分后的依赖关系

每个独立设计章节文件的 frontmatter 里要有 `depends_on` 字段，列出依赖的其他章节（始终包含 `00-brief`）。依赖关系在规划阶段确定并写入 `PROGRESS.md`，整体依赖图要有一个全局视角，不能只散落在各自文件的 frontmatter 里。

细化某章节或就地细化某步骤前，只加载直接依赖的内容，不要顺手把所有文档都带进来。无关内容带进来只会稀释注意力。
