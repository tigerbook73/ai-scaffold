# UI 变更测试覆盖规范

> 约束对象：UI 变更行为。回答"改了 UI 之后要做什么"。
> 本规则补充测试要求和强制检查义务。

---

## 关键变更的判定

| 变更类型                                                            | 需要测试 |
| ------------------------------------------------------------------- | -------- |
| 新增/删除影响用户操作路径的关键元素（表单、导航入口、核心业务操作） | ✅       |
| 修改页面级布局或渲染逻辑                                            | ✅       |
| 新增完整用户流程（认证、数据提交、多步骤表单等）                    | ✅       |
| 修改复杂交互组件的内部逻辑（状态管理、条件渲染）                    | ✅       |
| 纯展示性变更（无交互的布局调整）                                    | ⛔ 豁免  |
| 样式微调、文案修改                                                  | ⛔ 豁免  |

---

## 测试类型选择

```
关键工作流（表单提交、核心业务操作、导航、认证流程）
  → E2E（Playwright）

组件内部交互逻辑复杂、E2E 难以精准定位的场景
（如状态更新、条件渲染逻辑）
  → 组件测试
```

---

## 检查义务

修改 UI 文件时，必须执行以下四步：

1. **扫描测试文件**：grep 项目测试文件，确认是否有现存测试覆盖当前组件/页面
2. **判断是否触发关键变更**：对照上方判定表
3. **若触发但无测试**：主动提示用户，说明建议补充的测试方向（E2E 或组件测试）及豁免理由
4. **若触发且有测试**：检查现存测试中的定位器是否因本次 UI 变更而失效

**禁止静默跳过：** 无论是否需要补充测试，都必须向用户汇报检查结论。

---

## 豁免记录要求

豁免情形需在 PR/commit message 中注明原因。
